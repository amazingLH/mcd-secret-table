# 项目说明：麦麦密桌 SecretTable

## 1. 要解决的问题

同学聚餐、实验室夜宵或办公室拼单，经常同时存在三种困难：

- 个人预算、口味和营养要求不同，有人不愿公开解释自己的条件。
- 多数人喜欢的方案可能使少数人一直迁就；平均满意度高，不代表每个人都能接受。
- 大模型可以描述一份看似合理的套餐，但其中可能包含不存在的商品、错误价格或不可用的营养信息。

SecretTable 把任务拆成“模型提出方案、端侧检查个人条件、官方接口核实业务事实”。目标不是替用户付款，而是在明确边界内生成一份各人能接受、价格经过核验的餐单。

## 2. 创意与设计主张

项目的差异化在于三种机制的结合，不宣称任何单个概念为全球首创，也不宣称已经完成完整的同类产品检索证明。

| 设计 | 实现方式 | 对用户的价值 |
| --- | --- | --- |
| 信息最小化协商 | 原始个人条件在浏览器评估，向模型提供匿名评分和少量自愿接受组合 | 不必先在群里公开完整条件 |
| 最低满意度优先 | 全员接受后，优先比较最不满意的那个人，再比较平均分 | 不让“多数人的高分”掩盖少数人的拒绝 |
| 真实业务闭环 | 官方在售菜单、商品详情、营养记录、初始报价和最终整单核价 | 让生成结果受到实际商品与价格约束 |
| 可解释而非只给答案 | 编号补餐品名、候选分配、个人评分、采用标记和运行轨迹 | 能看懂为什么选、到底选了哪一份 |

当前是一个可运行的研究型应用原型：1 个大模型协调 Agent，配合每位参与者的确定性规则评估器。不是多个独立大模型在互相聊天。

## 3. 用户如何操作

1. 选择离线演示，或在本机完成模型计费确认后选择真实协商。
2. 设置共同城市、地点和公开总预算。
3. 在“01 本地条件舱”依次设置三位参与者的个人预算、口味、排除类别与可选营养边界。
4. 点击底部运行按钮。开始后个人条件区自动收起，但仍只在本页内存中。
5. 查看“02 候选方案与本地评估”：每份候选有编号、名称、参考总价、各人满意度、最低/平均分和接受人数。
6. 展开候选，查看每个人具体分到什么餐品。名称旁的编号用于和官方菜单、核价结果对应。
7. 真实模式若无人接受，模型根据反馈继续调整；最多三轮。
8. 候选全员接受后，按初筛排序依次做官方核价，并在浏览器重新检查个人条件。
9. “04 最终餐单”显示最终方案的名称和编号；它与候选区唯一的“最终采用”标记对应。
10. 用户可确认并下载餐单。确认不会创建订单，不会付款。

“03 运行轨迹”用于查看上述过程中的真实调用、本地评估、被淘汰候选与 Token 用量。离线模式只显示离线记录，不伪装成真实调用。

## 4. 1440、1450 是什么

它们是麦当劳接口返回的商品编码，不是金额、票数或评分。例如既有实测菜单中的 `1440` 对应麦辣鸡腿汉堡，`1450` 对应麦香鸡。页面根据**当前这桌实际获取的菜单**添加括号名称，不将这些例子作为永久商品字典。

显示示例：

```text
a1（参与者 1）只接受含1440（麦辣鸡腿汉堡）的组合（满意度=100）。
```

这只是可读性转换：发给模型、提交反馈和核价时仍使用原始商品编码。不会为了补一个商品名再调用一次模型。模型说明是生成理由，不是程序验证结论；如果说明与校验结果冲突，以校验结果为准。

## 5. 怎样从多份方案中选择

### 第一步：硬条件检查

每个人只判断分给自己的餐品。预算、排除类别、必需类别、热量上限、蛋白质下限等任何硬条件不满足，就拒绝该方案并记 0 分。存在未知商品，或在设置营养条件时营养记录缺失，也不能默认为通过。

### 第二步：计算满意度

通过硬条件后，由浏览器规则计算 0–100 分，考虑口味命中、预算余量、类别多样性和蛋白质加分。达到 55 分才接受。它不是模型“感觉上的分数”，也不是参与者手动投票。完整公式见 [技术架构与评分规则](./ARCHITECTURE.md#4-本地评分与排序)。

### 第三步：初筛排序

1. 全员接受的方案排在前面。
2. 比较最低满意度，越高越靠前。
3. 最低分相同时比较平均满意度。
4. 完全同分时按方案编号稳定排序。

下表仅是说明规则的假设示例，不是真实业务记录：

| 方案 | 三人的分数 | 全员接受 | 最低分 | 结果 |
| --- | --- | --- | --- | --- |
| A | 100、100、0 | 否 | 0 | 不进入最终核价 |
| B | 90、85、85 | 是 | 85 | 优先进入最终核价 |
| C | 95、75、80 | 是 | 75 | B 未通过复核时再尝试 |

### 第四步：核价与最终采用

真实模式按上述参考排序逐份核价，采用第一个满足官方总价、个人预算和其他个人条件复核的候选。因此，“全员接受”不等于“已经采用”，列表第一行也不保证一定是最后结果。候选区与最终区通过同一个方案编号对应。

这是**候选集合内的初筛与复核策略**，不是全菜单最优解，也没有对所有候选在最新核价后重新求一次全局最优。

## 6. 已达到的效果与限制

已有 DeepSeek 真实验收记录：两轮协商后获得全员通过的餐单，官方核价 ¥74.50，最低满意度 85。该记录证明这次运行链路成立，不代表所有条件、门店和时段必然成功。

原型尚未提供多设备房间、身份认证、密码学隐私、订单创建、付款、优惠券最优组合或完整菜单搜索。名称类别不等于过敏原信息，不能用于过敏安全保证。评分和自愿提供的组合仍可能泄露部分偏好。
